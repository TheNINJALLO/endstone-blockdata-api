## Endstone version policy

The command plugin's package dependency is **`endstone>=0.11.10`**, with no upper
bound. `api_version` remains `0.11`: it declares the public plugin API, not the
Endstone release number. The Endstone build for this new server package is
unknown, so its version and source commit remain `null` in the target profile.
The runtime version `26.50` is expected from the package name and still needs
confirmation from the matching Endstone server.

The minimum dependency permits installation on current and newer Endstone
versions; it is not a claim that future native layouts or Python bridge ABIs
are identical. Select the actual Endstone SDK and rebuild the native plugin and
Python bridge for that runtime before deployment. The Python wheel's existing
interpreter constraints remain in place until its bridge is rebuilt.

The existing exact adapter targets BDS 1.26.45 with Endstone 0.11.10. On an unmatched runtime it can use the public block-state adapter; full block-actor NBT, storage-item and player-inventory native features require a qualified adapter.

The historical release downloads and exact build matrix still describe their
original BDS/Endstone pairs. They are not 1.26.50.5 binaries. Raising the wheel's
minimum dependency also means the current source wheel is no longer intended
for the older 0.11.6/0.11.9 runtimes; use the historical release for those servers.

## Prepare either supplied package

Run from the project directory:

```sh
python scripts/prepare_bds_target.py --archive ../bedrock-server-linux-1.26.50.5.zip --platform linux-x64 --output build/target-linux.json
python scripts/prepare_bds_target.py --archive ../bedrock-server-windows-1.26.50.5.zip --platform windows-x64 --output build/target-windows.json
```

Add `--endstone-version VERSION` once the version is known. The tool accepts
0.11.10 and newer numeric releases, including development builds, and rejects
older or malformed versions. It does not download or choose an Endstone build.

An archive can be renamed without changing the result. Changed server bytes,
wrong-platform executables and mismatched fingerprints are rejected.

A successful preparation report has `server_files_verified: true` and
`native_adapter_qualified: false`. Add `--require-native` for a deployment gate:
it returns exit code 2 while native qualification is pending. Exit code 1 means
an input or verification failure; exit code 0 means preparation succeeded.

## Complete the native port

1. Obtain the Endstone SDK and runtime that support this exact BDS package.
2. Verify the adapter's private types, symbol addresses, vtable slots and
   instruction fingerprints against both server platforms and that SDK/runtime.
3. Build the plugin and its Python bridge against the selected Endstone,
   matching the runtime's Python and pybind11 ABI.
4. Run the project's native load, gameplay, persistence and shutdown checks
   on a disposable server before publishing a release for this target.

Existing exact adapter guards remain active. The new server hashes must not be
substituted into an old native profile while retaining its old offsets.
